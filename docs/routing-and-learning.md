# Routing rules and learning

This document describes behavior in the current `airo-ai-router` release. For the planned provider registry, portable learning, Jev feedback, encrypted sync, and research-consent milestones, see [Routing platform roadmap](routing-platform-roadmap.md). [Jev and AIRO](jev-and-airo.md) records the planned narrower role for Jev.

AIRO makes a routing decision in two parts:

1. Select a provider (`claude`, `codex`, `gemini`, or `copilot`).
2. Select a model tier (`fast`, `balanced`, or `deep`) and use the configured model plus any effort control implemented by that provider adapter.

In an adaptive workflow, AIRO repeats this decision for every phase. Analysis, implementation, validation, and review can therefore use different providers or model tiers.

## Decision precedence

The effective precedence, from strongest to weakest, is:

1. Explicit command-line overrides such as `--agent`, `--model`, `--tier`, and `--effort`.
2. A provider, model, or tier explicitly named in the current task.
3. The first matching custom configuration rule.
4. Phase preferences in an adaptive workflow.
5. Built-in task signals, routing policy, and evidence learned from similar work.
6. `defaultAgent` when the provider scores are tied.

Persistent UI or interactive preferences act as defaults. A provider or model named in the current task takes precedence over those preferences.

An explicitly selected provider is pinned. If its CLI is unavailable or becomes unusable, AIRO reports the failure instead of silently switching providers. Automatically selected providers may fall back when an eligible alternative is available.

## Custom configuration rules

Custom rules are user-authored entries in the active AIRO configuration. They are not generated by learning.

```json
{
  "rules": [
    {
      "name": "Native crash investigation",
      "agent": "claude",
      "modelTier": "deep",
      "effort": "high",
      "pattern": "(ios|android|xcode|gradle).*(crash|race|root cause)"
    }
  ]
}
```

Each rule supports:

| Field | Meaning |
| --- | --- |
| `name` | Human-readable name shown in the routing explanation. |
| `pattern` | Case-insensitive JavaScript regular expression tested against the task. |
| `agent` | Optional provider selection. |
| `modelTier` | Optional `fast`, `balanced`, or `deep` selection. |
| `effort` | Optional reasoning-effort override. |

Rules are evaluated in array order, and only the first match is applied. A malformed regular expression is ignored. A rule that selects an agent also gives that provider 100 scoring points, so it is decisive unless a stronger explicit selection overrides it.

AIRO loads the first configuration file it finds in this order:

1. `<repository>/.airo.json`
2. `<repository>/.ai-router.json`
3. `~/.config/airo/config.json`
4. `~/.config/ai-router/config.json`

It does not merge rule arrays from several configuration files.

## Task features and provider capabilities

AIRO first extracts provider-neutral task features: category, risk, complexity, language, and local hashed tokens. The source-controlled provider registry declares reviewed cold-start weights for task categories, high-risk work, and fast or complex tasks. There are no separate Claude and Codex keyword-scoring tables.

For every decision, AIRO generates a candidate for each registered provider and each `fast`, `balanced`, and `deep` tier. A candidate's initial score combines:

- The provider's capability score for the task features
- Tier suitability for the calculated complexity
- An optional configured policy bias
- Time-decayed evidence learned from similar local outcomes

Custom rules and explicit choices retain their higher precedence. Cold-start capability values are versioned source data, not self-modifying production weights; they require tests and review when changed.

The provider with the highest total score wins. If several providers tie and `defaultAgent` is among them, `defaultAgent` wins; otherwise AIRO uses the first highest-scoring provider in its candidate order.

## Current fallback behavior

Automatic fallback uses the source-controlled provider registry:

1. Exclude the selected provider and every provider already ruled out during this run.
2. Rank the remaining providers by their task-specific routing score.
3. Break equal scores with the stable registry priority: Claude, Codex, Gemini, then Copilot.
4. Skip commands that are not available.
5. After authentication or usage-limit failure, also skip a candidate whose adapter confirms that it is signed out.

Gemini and Copilot do not yet have account probes, so their authentication state is unknown until execution. Missing-command fallback checks executable availability only. An explicitly selected provider never falls back.

## Complexity and model tier

Complexity begins at `2` and is clamped to the range `1` through `5`.

It increases for signals such as:

- Long or compound tasks
- Architecture and root-cause work
- Race conditions or intermittent failures
- Security-sensitive changes
- Migrations and cross-module constraints

It decreases for signals such as:

- Typos, formatting, and renames
- Simple type or unit-test work
- Explicitly small or single-file changes

The result maps to a tier:

| Complexity | Tier |
| --- | --- |
| 1–2 | `fast` |
| 3 | `balanced` |
| 4–5 | `deep` |

The selected provider's configuration maps that tier to a concrete model and an optional effort value. Claude and Codex currently receive their configured effort controls; Gemini and Copilot do not, so their tiers differ by model selection and retain `auto` effort. A tier is an automatic profile, not a model allowlist.

## Adaptive phase preferences

When orchestration is active, the phase plan supplies defaults suited to each type of work:

| Phase | Default provider | Typical tier |
| --- | --- | --- |
| Analyze | Claude | `balanced`, or `deep` for critical work |
| Implement | Codex | `fast`, `balanced`, or `deep` according to scope |
| Validate | Codex | Usually `fast` |
| Review | Claude | `balanced`, or `deep` for critical work |

These preferences do not replace a provider, model, or tier explicitly selected by the user.

## What learning stores

Learning is local, file-based, and repository-scoped by default. AIRO does not train a provider model or maintain a separate learned-weights file.

The current release does not sync history between machines. Portable encrypted export/import and optional end-to-end encrypted cloud sync are roadmap items, not current commands. Until those milestones ship, users must treat the files below as local data and migrate them manually if needed.

Unless `history.path` is configured, records are stored at:

```text
~/.local/share/airo/history.jsonl
~/.local/share/airo/history.feedback.jsonl
```

Older installations may continue using `~/.local/share/ai-router/` until their data is migrated.

### Phase history

`history.jsonl` contains one JSON object per completed phase. Each record includes:

- Run, session, phase, and timestamp identifiers
- Working-directory path
- Original task and generated phase prompt
- Provider, model, tier, effort, and calculated complexity
- Exit code, duration, retry count, and recovery count
- A configured-length excerpt from the provider output
- Provider token telemetry when available
- Extracted task features
- Deterministic evaluation and outcome data

Because the original task and an output excerpt are persisted, the history file can contain project-sensitive text even though it remains local.

Task features contain a category, detected language, risk level, complexity, normalized tokens, and a 64-dimensional embedding. The embedding is generated locally by hashing tokens and adjacent token pairs; it is not produced by an external embedding service.

### Feedback history

`history.feedback.jsonl` stores feedback separately from phase records. A feedback record contains:

- A target run or phase
- A `good` or `bad` rating
- An optional note
- Whether the source was explicit or implicit
- A confidence value

Phase feedback takes precedence over run feedback. Explicit feedback normally has confidence `1`. A clear corrective follow-up such as “fix that” or “try again” can create implicit negative feedback with confidence `0.45`. Silence is not treated as positive feedback.

## How history influences a new route

For each new task, AIRO calculates learning hints from existing records at routing time:

1. Restrict records to the current repository when `repositoryScoped` is enabled.
2. Compare the new task with stored tasks.
3. Discard records below `similarityThreshold`.
4. Keep at most the 30 closest observations.
5. Convert explicit feedback or deterministic outcomes into rewards and penalties.
6. Reduce the weight of older evidence using `halfLifeDays`.
7. Calculate provider boosts, tier boosts, and utility for each provider/model/effort route.
8. Apply learned changes only after `minimumSamples` effective observations exist.

Task similarity combines:

| Component | Weight |
| --- | --- |
| Lexical token overlap | 60% |
| Hashed-vector cosine similarity | 30% |
| Matching task category | Up to 6% |
| Matching language | Up to 2% |
| Matching risk | Up to 2% |

Route utility primarily reflects the observed reward, with smaller penalties for token use and duration. Explicit feedback is the strongest evidence. Automatic evaluation uses process success, reported verification, missing verification, retries, recoveries, and later regression findings with lower confidence.

Learned evidence cannot override an explicitly selected model or tier. A learned tier must also beat the current choice by the thresholds defined in the router. Controlled exploration can occasionally choose an under-observed tier, but it is disabled by default.

## Learning configuration

```json
{
  "history": {
    "enabled": true,
    "learningEnabled": true,
    "similarityThreshold": 0.25,
    "minimumSamples": 2,
    "halfLifeDays": 90,
    "explorationRate": 0,
    "repositoryScoped": true
  }
}
```

- `enabled` controls whether history and feedback are read and written.
- `learningEnabled` allows history to affect routing. Set it to `false` to retain records without learning from them.
- `similarityThreshold` sets the minimum similarity for an observation to participate.
- `minimumSamples` prevents route changes based on insufficient evidence.
- `halfLifeDays` controls how quickly older evidence loses weight.
- `explorationRate` is the probability of selecting an under-observed tier when no learned route already wins.
- `repositoryScoped` prevents evidence from one working directory from influencing another.

## Inspecting decisions and evidence

Preview a routing decision without running a provider:

```bash
airo --dry-run --explain "migrate this legacy module"
```

Inspect routing history and learning evidence:

```bash
airo history 20
airo learning status
airo learning explain <run-or-phase-id>
```

Provide explicit feedback:

```bash
airo feedback good
airo feedback bad "used more reasoning than necessary"
airo feedback phase <phase-id> good "implementation was correct"
```

Reset feedback-derived learning evidence:

```bash
airo learning reset --yes
```
